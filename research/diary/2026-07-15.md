### INCIDENT: random-mutation agent writes to the wrong hypothesis-id path from round 2 onward

**Status: harness bug, confirmed with evidence. Blocks E1b data
collection specifically, does not block the harness-core burn-in
verdict below.**

**Observed:** Round 1 (3 slots) failed as designed, a real gate class,
`formal_failed`, on `insn_sh_ch0` / `insn_srli_ch0` / `reg_ch0` (mutated
RTL genuinely caught by riscv-formal; this is the control working).
Round 2 (3 slots) all failed with `hypothesis_gen_failed: Hypothesis
agent did not write a file for slot <id>`, an infrastructure failure,
not a gate class. Evidence: `/tmp/bench-burnin/random-mutation/rep1/log.jsonl`
rows for `round_id: 2`, all three `error` fields identical modulo slot
id; `orchestrator.log:191-199` shows round 2's correct pre-allocated
IDs (`hyp-20260715-001-r2s0`, `-002-r2s1`, `-003-r2s2`) followed
immediately by all three reporting `did not write a file`.

**Root cause (confirmed via the agent's own debug logs plus source
inspection, no speculation):** each round-2 slot's
`.agent.hyp-*-r2s*.log` under
`cores/bench/experiments/hypotheses/` reads
`[random-agent] wrote cores/bench/experiments/hypotheses/hyp-20260715-001-r1s0.yaml`
for all three round-2 slots: the agent wrote to a **round-1** id, not
its own round-2 id, and all three slots collided on the *same* wrong
path.

Mechanism: `tools/agents/hypothesis.py:_build_prompt()` places
`history_section` (built from `_recent_outcomes()`, listing prior
rounds' hypothesis IDs, lines 278-293) **before** `id_clause` (states
"Use exactly this hypothesis ID: `<real target id>`", line 318) in the
assembled prompt string (line 299 f-string, `history_section` at line
309, `id_clause` at line 318). `tools/agents/random_agent.py:_hyp_id()`
(line 169-171) extracts "the" id via `_HYP_ID.search(prompt)` (leftmost-match, not "last match" or "match after a specific marker").

Round 1: `log_tail` has no hyp-id-shaped entries yet, so
`_recent_outcomes` contributes zero regex matches; `.search()` finds
the only match, which is the correct id in `id_clause`. Works.

Round 2+: `_recent_outcomes` now lists round-1's ids (e.g.
`hyp-20260715-001-r1s0`) textually before `id_clause`'s real id;
`.search()`'s leftmost-match semantics grab the stale id instead. All
three round-2 slots share the identical `history_section` (same
`log_tail` for the whole round), so they deterministically collide on
the same wrong id. This is why all three `.agent.*.log` files show
the identical wrong write target, not three different wrong targets.
The orchestrator's `allowed_yaml_ids` whitelist then finds no file at
any of the three real round-2 paths and reports `hypothesis_gen_failed`
for all three.

**Scope:** deterministic, not flaky. Will reproduce on every round ≥ 2
of every random-mutation rep as currently implemented. The E1b prereg
(`research/runs/EXP-2026-07-e1b-random-control/prereg.yaml`) calls for
N=15 rounds × K=3 × reps=3. Under this bug, only round 1 of each rep
can ever produce valid gate-class data; rounds 2-15 would all read as
infrastructure failures, corrupting `accepted_count`,
`gate_pass_rate`, and `first_failing_gate_distribution` (three of the
prereg's four secondary metrics).

**Not fixed here:** `tools/agents/random_agent.py` and
`tools/agents/hypothesis.py` are both `tools/` sources; fixing them is
a separate reviewed task per this task's dispatch. No source was
modified while diagnosing.

**Decision:** `blocked` for the E1b arm. The random-mutation control
must not be used for E1b data collection until `_hyp_id()` (or the
prompt ordering) is fixed and the random rep is re-run to confirm
rounds ≥2 resolve real gate classes, not `hypothesis_gen_failed`.
